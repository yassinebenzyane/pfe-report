\chapter{Realization}

\section{Introduction}

This chapter presents the realization of the AgriConnect system, translating the conceptual design and architecture defined in the previous chapter into a fully functional solution.

The implementation phase covers several key aspects of the system, including the setup of the development environment, the deployment of the database structure, and the integration of external services. In particular, the system relies on Supabase for data management and storage, and integrates WhatsApp as the primary communication channel to ensure accessibility for farmers.

A central component of the implementation is the use of automated workflows, developed using n8n \cite{n8n2024}, which handle message reception, processing, orchestration, and knowledge base ingestion. For example, the message reception workflow manages incoming WhatsApp messages, verifies user existence, processes different media types, and stores structured data for further processing.

In addition, the system incorporates a multi-agent architecture where each agent is responsible for a specific task, such as message normalization, orchestration, information retrieval, vision-based analysis, and escalation handling.

The chapter also presents the implementation of the web application, which provides dedicated interfaces for different types of users, including farmers, agronomists, administrators, and visitors. This interface complements the WhatsApp interaction by offering advanced functionalities such as case tracking, management, and system supervision.

Finally, the chapter introduces the knowledge base implementation, which enables the system to store, process, and retrieve agricultural information efficiently through vector-based search mechanisms \cite{li2025llm}.

Overall, this chapter demonstrates how the different components of AgriConnect are implemented and integrated to deliver a coherent and intelligent agricultural support platform.

\section{WhatsApp Integration}

WhatsApp serves as the primary interaction channel for farmers in the AgriConnect system. It was chosen for its widespread adoption and ease of use, particularly in rural areas where smartphone usage is common but access to web applications may be limited \cite{anrt2025}.

The integration is implemented through \textbf{WasenderAPI}, a third-party WhatsApp Business API gateway that provides a REST interface for sending and receiving messages. WasenderAPI manages the WhatsApp session and handles all low-level communication with the WhatsApp platform, including media encryption and delivery.

Incoming messages from farmers are delivered to the system via a \textbf{webhook} endpoint registered in n8n. Each time a message is sent by a user, WasenderAPI sends an HTTP POST request to this endpoint containing the full message payload. The system supports three types of incoming messages:

\begin{itemize}
    \item \textbf{Text messages:} the most common type, directly processed and forwarded to the pipeline.
    \item \textbf{Audio messages (voice notes):} decrypted and transcribed to text using the OpenAI Whisper model before processing.
    \item \textbf{Image messages:} decrypted and stored in Supabase Storage for visual analysis by the Vision Workflow.
\end{itemize}

Outgoing responses can be sent either as text messages or as audio messages. For audio responses, the system generates speech using a text-to-speech service, uploads the audio file to Supabase Storage, creates a signed URL, and transmits it to the farmer via WasenderAPI\@.

\section{Workflow Implementation}

The business logic of the AgriConnect WhatsApp pipeline is implemented as a set of automated workflows in n8n. Four main workflows handle message reception, orchestration, visual analysis, and knowledge base ingestion.

\subsection{W00 — Message Reception Workflow}

The W00 workflow is the entry point of the WhatsApp pipeline. It is triggered by every incoming message received via the WasenderAPI webhook and is responsible for receiving, validating, preprocessing, and buffering each message before it reaches the orchestration layer.

The workflow begins with a \textbf{Webhook} node that listens for POST requests from WasenderAPI\@. Upon reception, the \textbf{Normalize Incoming Message} node parses the raw payload and extracts the essential fields: the sender's phone number, the message type, the text content, the media URL, and the MIME type.

The system then verifies whether the sender is a registered farmer by querying the Supabase database through the \textbf{Check Farmer Exists} node. If the farmer is not found, the workflow sends a registration invitation via WhatsApp and stops processing. If the farmer is registered, the message is forwarded to the \textbf{Route Types} node, which dispatches it to one of three branches based on the message type.

For \textbf{text messages}, the content is first passed through a \textbf{Guardrails} node that detects inappropriate or off-topic content. Messages that fail the guardrails check trigger a rejection response; those that pass are pushed into the Redis buffer.

For \textbf{audio messages}, the workflow decrypts the audio file using the WasenderAPI decryption endpoint, downloads it, and sends it to the OpenAI Whisper transcription model \cite{openai_whisper2022}. The resulting text is then pushed into the Redis buffer.


For \textbf{image messages}, the workflow decrypts the image, downloads it, and uploads it to the Supabase Storage bucket under a path structured by sender and message identifier. A reference to the stored image is then pushed into the Redis buffer.

Once the message is processed, the \textbf{Redis Buffer — Push Message} node appends the structured entry to a Redis list keyed by the sender's phone number. The \textbf{Redis Buffer — Update Last Activity} node then sets a key with a 15-second time-to-live, indicating the moment of last activity. This mechanism allows the orchestration workflow to detect when a conversation has been idle long enough to trigger batch processing.

\subsection{W01 — Orchestrator Workflow}

The W01 workflow is the central processing pipeline of the AgriConnect system. It is responsible for reading buffered messages, normalizing and persisting them, orchestrating all AI agents, and delivering the final response to the farmer via WhatsApp.

On each execution, the workflow scans Redis buffer keys and identifies completed conversation batches. When an image is detected, a signed URL is generated and the image is passed to Ollama/LLaVA for preliminary visual observation. The Normalizer Agent then structures the batch into a validated JSON object, persists it in Supabase, and clears the Redis buffer. The Orchestrator Agent loads the farmer's profile and conversation history, selects the appropriate sub-agents, and produces a final response routed as text or audio to the farmer.

\subsection{Vision Sub-Workflow}

The Vision Sub-Workflow is a specialized pipeline called by the Orchestrator Agent when a farmer sends an image and the visual analysis conditions are met. Its purpose is to identify the plant species, detect potential diseases, and recognize the crop variety based on the submitted image.

The workflow accepts three inputs: the image URL, an initial visual observation extracted during preanalysis, and the farmer's question translated into English. A normalization step preprocesses these inputs and determines which PlantNet identification endpoints should be called based on keyword detection in the question.

Four parallel identification calls are then executed against the PlantNet API \cite{plantnet2024}:

\begin{itemize}
    \item \textbf{Species Identify — All}: a general species identification call that returns the most probable plant species from a broad botanical database.
    \item \textbf{Species Identify — KT}: a second species identification call using the K-World Flora reference dataset, used to cross-validate and strengthen the species hypothesis.
    \item \textbf{Disease Identify}: detects potential diseases or pathological symptoms visible in the image, returning candidates such as leaf spots, fungal infections, or blight.
    \item \textbf{Variety Identify}: attempts to identify the specific cultivar or variety of the detected species, useful for crops where variety influences susceptibility and treatment.
\end{itemize}

The results from these four calls are merged and normalized into a single structured output. This output contains ranked lists of species candidates, disease candidates, and variety candidates, each with a confidence score. A final status field indicates whether the evidence is sufficient for reliable analysis, and a recommended next step guides the orchestrator toward either requesting a better image or invoking the RAG agent for further analysis.

\subsection{KB Ingestion Workflow}

The KB Ingestion Workflow automates the process of populating the AgriConnect knowledge base with agricultural documents. It is triggered automatically whenever a new file is created in a designated Google Drive folder named \textit{Knowledgebase}.

Upon detection, the workflow extracts the file metadata including the file identifier, name, and MIME type. A deduplication step ensures that each file is processed only once per ingestion event, even if the trigger fires multiple times. Before loading the new content, the workflow sends a DELETE request to Supabase to remove any existing document chunks associated with the same file identifier, preventing duplicate entries in the vector store.

The file is then downloaded from Google Drive and passed to the document loader, which parses the DOCX content and splits it into manageable chunks. Each chunk is enriched with metadata fields including the source file identifier and file name, ensuring that stored chunks remain traceable to their origin. The chunks are then vectorized using the OpenAI text embedding model and inserted into the Supabase \texttt{documents} table, which serves as the vector store for the RAG agent.

Once ingestion is complete, the workflow sends an email notification to the system administrator confirming the successful ingestion and reporting the number of chunks inserted.

\section{Web Application}

The AgriConnect web application complements the WhatsApp channel by providing role-specific interfaces for farmers, agronomists, administrators, and visitors. Two independent Next.js applications share a common Spring Boot REST API backend (exposed at \texttt{/api/users}, \texttt{/api/cases}, etc.) and a Supabase storage layer. Authentication relies on Supabase JWT tokens, and role-based access control is enforced at both frontend and backend levels.

\subsection{Authentication and Role-Based Access}

Authentication uses Supabase email/password credentials. Upon login, a JWT is generated and included in every API request. The backend extracts the user identity from the token and retrieves the role from the database, redirecting farmers to their dashboard and agronomists to theirs. Backend endpoints are also protected by role-based access control, and the admin interface is deployed as a separate application restricted to administrator accounts.

\section{Knowledge Base}

The knowledge base is implemented using the pgvector extension \cite{pgvector2024} on Supabase. Agricultural documents (crop diseases, treatments, irrigation, soil management) are stored as text chunks in a \texttt{documents} table alongside their OpenAI vector embeddings \cite{li2025llm}. The RAG Agent retrieves relevant chunks via cosine similarity search on the farmer's query embedding. Incremental updates are supported: re-uploading a document to Google Drive triggers automatic deletion of outdated chunks and re-ingestion of the new version.
